Shell Hooks guide

Shell Hooks runs your own shell scripts when Code on the Go opens a project, opens, saves or closes a file, or starts or finishes a build. If you can write a shell script, you can fit the IDE into your workflow.

Nothing runs until you turn on Run hooks in Preferences > Shell Hooks. Hooks only report what happened: a script cannot stop a save or a build.

Your first hook

  1. Preferences > Shell Hooks: turn on Run hooks, then tap Create sample hooks.
  2. In the Terminal: 
    cd ~/.config/codeonthego/hooks
mv file-saved.sample file-saved
chmod +x file-saved
  3. Save a file. The Hooks tab in the bottom panel shows the run; tap it to see the output. The sample adds a line to ~/codeonthego-hooks.log.

Where scripts go

~/.config/codeonthego/hooks/
  file-saved          runs first
  file-saved.d/       then every script here, in name order
  actions/            "Run <name>" on a file's menu
  • Only executable files run: chmod +x.
  • Files ending in .sample or ~, or starting with ., never run.
  • #!/usr/bin/env python3 or #!/bin/bash use the Terminal's programs. No shebang means bash.
  • Settings can turn single hooks off without deleting their scripts.

Actions

An executable script in hooks/actions/ appears as Run <name> when you long-press a file in the file tree or an editor tab. It runs in the Terminal with the file in $1, so you see its output.

Timeouts and order

Scripts run one at a time, in the order things happened: your scripts first, then the project's. A script still running after the timeout (60 seconds by default, set in Preferences) is stopped. Up to 64 events can wait; after that the oldest is dropped. Run long jobs in the background: nohup long-job >/dev/null 2>&1 &

Hooks stored in a project

A project can carry its own hooks in .codeonthego/hooks/, with the same layout. They run only if you turn on Run hooks stored in projects and trust each script.

Why: a hook runs with the same access as the Terminal, including your files and the network. Any plugin that can write files, or an AI agent, can put a script into a project. If such scripts ran by themselves, they could run commands you never approved.

  • An untrusted script is skipped and listed in the Hooks tab. Review shows the whole script; Trust approves exactly what you read.
  • Editing a trusted script, or adding one, needs a new review.
  • Preferences lists the projects you trusted scripts in; Revoke forgets them.
  • A trusted script runs from a private copy of what you approved, so it cannot be swapped after you approve it. Use $COGO_HOOK_SCRIPT to find the original.

Your own hooks are trusted

Scripts in ~/.config/codeonthego/hooks/ are yours, so they run without review once hooks are on. Like anything you run in the Terminal, they can read and change your projects and use the network.
