1. Executive Overview

Shell Hooks lets anyone who can write a shell script fit Code on the Go into the workflow they already have, with no Android development. Drop an executable script named after a hook into ~/.config/codeonthego/hooks/ and it runs at that moment: when a project opens, when a file is saved, when a build fails. The file or project arrives in $1, exactly as a git hook gets its arguments.

Typical uses: pull the latest changes when a project opens, run a linter or formatter on save, copy a fresh APK to a shared folder when a build succeeds, or post a message when one fails.

The plugin is off until you turn it on in Preferences → Shell Hooks. Hooks only report what happened: a script cannot stop a save or a build.

Folder layout

~/.config/codeonthego/hooks/
  file-saved            runs first
  file-saved.d/
    10-format           then these, in name order
    20-lint
  build-failed.sample   never runs: rename it and chmod +x to use it
  actions/
    word-count          "Run word-count" on a file's menu
  • In your folder, only files with the executable bit run (chmod +x). A project's scripts need no executable bit: projects sit on shared storage, which keeps none.
  • Names ending in .sample or ~, and names starting with ., never run, so an editor's swap file is never executed.
  • A shebang under /bin, /usr/bin or /usr/local/bin, such as #!/usr/bin/env python3 or #!/bin/bash, is resolved to the Terminal's program, as in the Terminal. Any other interpreter path, such as a virtualenv's python, runs as written. A script with no shebang runs with bash.
  • Create sample hooks in settings writes one .sample per hook, documenting its arguments.

Actions

Executable scripts in hooks/actions/ appear as Run <name> when you long-press a file (not a folder) in the file tree or an editor tab. They run in the visible Terminal, with the file in $1, so you see what they print. An action that cannot start is listed in the Hooks tab with the reason.

Hooks tab

The Hooks tab in the editor's bottom panel lists the last 100 runs: hook, script, file, outcome, exit code, time and duration. Tap a run to see its output (the last 64 KB). Project scripts waiting for review are listed above the runs.

Timeouts and ordering

Scripts run one at a time, in the order their events reach the plugin, global scripts before project scripts. The IDE reports project and save events through a thread of its own, so a save just before a build can be reported after the build starts. A script still running after the timeout (60 seconds unless you change it) is stopped, and with the Terminal's timeout (coreutils) installed so is every program it started. Disabling, unloading or updating the plugin while a script runs stops it the same way within a few seconds; release builds of Code on the Go ship timeout, and without it only the script's own process is stopped. If events arrive faster than scripts finish, up to 64 wait; past that the oldest is dropped. Start long jobs in the background (nohup long-job >/dev/null 2>&1 &).

3. Security Model

A hook runs with Code on the Go's own access, the same as a command typed in the Terminal: it can read and change your projects and use the network. Who wrote the script decides whether it can run.

  • Your hooks in ~/.config/codeonthego/hooks/ are scripts you put there yourself, so they run once hooks are on.
  • Project hooks in a project's .codeonthego/hooks/ come with the project: from a cloned repository, an AI agent's edit, or a plugin that can only write project files. A project hook would otherwise run commands you never approved. They therefore need two things: the Run hooks stored in projects switch (off by default), and your trust in that exact script. An untrusted script is skipped and listed in the Hooks tab; Review shows all of it, one numbered row per line, before you can trust it. Text that wraps continues on the same number, so a wrap never reads as a new line.
  • Only plain scripts can be trusted. A project script can be reviewed only if it is at most 64 KB of printable ASCII and newlines: no tabs, no carriage returns, no other control or non-ASCII characters, no line longer than 100 characters or ending in a space, and a name of letters, digits, ., _, - and /. Anything else is listed with the reason it can't be reviewed, and never runs. Each of these can make a script run differently from how it reads: a no-break space bash takes as part of a word, a backslash before an invisible carriage return or trailing space that looks like a line continuation, a long run of spaces whose wrap looks like a new line, a tab that looks like a space where <<- tells them apart. Your own hooks have no such limits.
  • Trust is recorded per project, per script path, against the SHA-256 of the script's bytes. Editing the script, or adding another, needs a new review. Settings lists the trusted projects, each with Revoke.
  • A trusted project script runs from a private copy of the bytes you trusted, so it cannot be swapped between the check and the run.
  • File names and other values reach hook scripts as separate arguments, never through a shell command line, so a file named $(rm -rf ~) is just a name. Actions are the exception: the Terminal takes a command line, so an action's command is built with every value in single quotes, which the shell never expands.
  • What review does not cover. A plugin that can run commands, or one that writes files from inside the IDE, can already change your own hooks folder or the record of what you trusted. Install only plugins you trust. Trust also covers only the hook's own text: files it runs from the project, such as ./gradlew or ./scripts/setup.sh, are not reviewed and can change later. Keep project hooks self-contained, or review what they call.

Permissions: system.commands to run scripts, filesystem.read for the file and project listeners, and filesystem.write to write the sample hooks. On an IDE older than 26.47 the plugin still loads; project-opened, project-closed and file-saved never run there. Actions need the Terminal service plugins got in 26.42; on an older IDE, "Run <name>" records a run that did not start.

Not hooked on purpose: editor content changes (one process per keystroke). Hooks cannot veto: every IDE callback here reports something that already happened.

6. Deployment & Usage

Build the installable plugin from the plugin folder:

cd plugins/Shell-Hooks
../../gradlew assemblePlugin

The .cgp lands in build/plugin/shell-hooks.cgp. Install it with the Plugin Manager, then:

  1. Open Preferences → Shell Hooks and turn on Run hooks.
  2. Tap Create sample hooks.
  3. In the Terminal: cd ~/.config/codeonthego/hooks && mv file-saved.sample file-saved && chmod +x file-saved
  4. Save a file, then open the Hooks tab to see the run. The sample appends a line to ~/codeonthego-hooks.log.

7. Key Benefits

  • No Android development. Anything a shell script can do becomes an IDE integration.
  • Familiar model. Named scripts and .d folders, as in git hooks and run-parts.
  • Safe by default. Off until enabled; project scripts need your review; hook values never pass through a shell parser.
  • Visible. Every run's outcome and output in one tab.
