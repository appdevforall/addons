# Exit codes of `libpart1_membw.so` and `libpart1_gpubw.so` (engine 0.2.4)

Every exit other than 0 prints **one JSON object** on the last stdout line (with or without `--json`), a one-line message on stderr, and exits with the code below.
A success prints JSON only with `--json`. Without `--json` `libpart1_gpubw.so` behaves as the kit binary: a good `--loop-seconds` run and a run in which every variant is skipped exit 0 with no JSON line; the guard that a row is never `ok` without a number applies only with `--json`. The JSON has `status`, `exit_code` and, for a refusal or error, a `reason` (also appended to `conditions.note`; `reason` is an optional field of the row schema). With `--static-probe` (membw) and `--probe` (gpubw; engine 0.2.2) the object is a `part1-staticprobe-v1` / `part1-gpuprobe-v1` object (same `status`, `exit_code`, `reason`; the codes that can occur are 0, 2 and 124: no gate, no pin, no memory guard; no Vulkan device is exit 0 with `vulkan.available false`). With `--pin-probe` the object is a `part1-pinprobe-v1` object instead of a row (same `status`, `exit_code`, `reason`; the codes that can occur are 0, 1, 2, 97 and 124: exit 1 when the CPU list cannot be read (`/proc/cpuinfo` and the affinity mask both unusable), and a CPU that does not pin is reported in `cpus` and does not change the exit code).

| Code | Name | `status` in the JSON | Meaning | Kit equivalent |
|---|---|---|---|---|
| 0 | ok | `ok` | The row was measured and (with `--json`) reported. | 0 |
| 1 | failed | `failed` | Measurement or runtime failure: a kernel verification guard mismatched (read XOR, write/copy spot check, pacer chain), `mmap` or an allocation failed, a Vulkan call failed, a dispatch verification failed. Also: the CPU list could not be read (`/proc/cpuinfo` and the affinity mask both unusable; the kit exited 2 there; this is also the one way the pin probe exits 1) and, with `--json` only, the internal guard that a row is never `ok` without a number. | 1 |
| 2 | usage | `failed` | Bad, unknown or missing option or value; a `--row-kind` that is not a schema `kind`; options not allowed with `--json` (`--split`, `--suite`, several GPU variants, `--loop-seconds`); a GPU mode or per-wg that would measure nothing (`gpubw --json`); options other than `--cores --spin-ms --json --gate --max-seconds` with `--pin-probe`; the same CPU twice in `--cores` (rows and the pin probe). Options other than `--json` and `--max-seconds` with `--static-probe` or `--probe` (0.2.2). A bad `--tier` value is refused before it is stored, so the record carries no `tier`. Nothing was measured. The record has no `tag` only when the error came before `--tag` was parsed (the app adds it). | 2 (the kit's unreadable CPU list is 1 here, see row 1) |
| 3 | unsupported | `unsupported` | The row cannot run on this device: DC ZVA with a block other than 64 B (K09); no Vulkan device, no compute queue, or no usable Vulkan memory type. | 3 (DC ZVA) |
| 87 | pin failed | `failed` | The pin did not hold within the kit's 5 s retry window (`pin_retry`, mask and running CPU verified) and `--allow-unpinned` was not given. `pin.result` is `failed`, `cpu_set` names the CPUs asked for, there is no `unpinned` label. With `--allow-unpinned` a CPU that failed is not retried again in the same process (one 5 s wait per CPU). | 87 (`PIN_RETRY_EXIT`) |
| 88 | memory | `skipped` | The buffers the row is about to allocate exceed `min(--mem-limit-mib, 55 % of MemTotal, 70 % of MemAvailable)`, or MemTotal/MemAvailable could not be read, or `--fit-buffer` would need less than 64 MiB per thread (GPU: per buffer). **Nothing was allocated or pinned.** | 88 (32-bit builds only) |
| 97 | not foreground | `skipped` | The gate is on and the program's own `/proc/self/cpuset` is not exactly `/top-app` (or cannot be read). Nothing was measured, allocated or pinned. `conditions.foreground_cpuset` holds what was read. | new (the kit gated in the shell) |
| 124 | timeout | `failed` | `--max-seconds` elapsed. A watchdog thread reports the row as failed with label `timeout` and exits; no outside `timeout` is needed. Any partial result is discarded. The timeout object is the last stdout line (stdout stays locked from the emit until `_exit`). The 124 record carries the pin facts known at that moment: `pin.result unpinned` and the label `unpinned` when a pin has failed under `--allow-unpinned` in an earlier run, an earlier sweep size or the run in progress (a `pin_retry` still waiting is not reported); its `cpu_set` names the CPUs asked for (rule below). | 124 (shell `timeout`) |

Not exit codes of the engine: 126/127 (the loader could not start the file, for example a missing `libvulkan.so`) and 137/139 (killed by a signal, for example the low-memory killer or `SIGILL` on a CPU without the instructions) come from the system, not from the program, and produce no JSON. The app should treat "no JSON line" as `failed` with the raw exit code.

## What `status` means for the row log

`status` follows `part1-rows-v1`: only `ok` rows feed descriptor leaves. `skipped` (88, 97) and `unsupported` (3) are expected, recorded refusals; `failed` (1, 2, 87, 124) is an error; `void` is never produced by the engine (only the app can know that it lost the foreground).

## One rule for `cpu_set` and `pin` (engine 0.2.2, made exact in 0.2.3 and 0.2.4)

`cpu_set` and `conditions.cpu_set` hold the CPUs the row asked for, with one exception: an `ok` row whose `pin.result` is `unpinned` has `cpu_set []` and `conditions.cpu_set null` (no CPU was pinned for all of it). Every record without a value (exit 1, 2, 3, 87, 88, 97 and the 124 record) names the CPUs asked for, whatever its `pin.result`, once they are known. The CPUs are known once `--cores` and `--threads` have been parsed and checked (for the pacer: at the start of `pace_main`, after the gate and the memory guard). A record written before that has `cpu_set []` and `conditions.cpu_set null`: every exit 2 raised while the options are parsed or checked; the exit 1 for an unreadable CPU list (it comes before `--cores` is parsed); and, **for the pacer only, the exit 97 and the exit 88** (a row or sweep refused with 97 or 88 names its CPUs). An exit 2 raised later names the CPUs: **a sweep size that is too small, whether it is the first size or a later one** (it carries `pin.result unpinned` when an earlier size ran unpinned). In a 124 record `pin.result` is `unpinned` when a pin is known to have failed (see row 124) and `not_applicable` otherwise. Exit 87 is `pin.result failed`. The 0.2.1 text "an unpinned row always has `cpu_set []`" is gone: it was not true for the 124 record. Details and the labels are in `ENGINE.md`.

Exit 2 for a sweep size that is too small (less than 256 bytes per thread, or not a number) has the reason `sweep size <size> too small`, where `<size>` is the size as given cut to its first 48 characters, without a mark (0.2.3; 0.2.2 and earlier read a freed buffer there).

Labels added in 0.2.2: `note_truncated` (any record: some note text did not fit and was dropped or cut) and `gpu_rate_unstable` (a GPU row whose largest dispatch rate is at least 1.25 times the smallest).
