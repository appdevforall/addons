# Part 1 engine 0.2.4 (ADFA-6876 jobs P1-03, P1-03F, P1-03G, P1-03H, P1-03I and P1-03J)

Two arm64-v8a programs, built as position-independent executables with plugin-extractable names (`lib*.so`, host `PluginLoader.kt` lines 150-180 extracts only `lib/<abi>/lib*.so`):

| File | Content | Dependencies |
|---|---|---|
| `out/arm64-v8a/libpart1_membw.so` | CPU read, write, copy, size sweep, prefetch-distance variants, pacer (kit `membw`) | libc, libm, libdl |
| `out/arm64-v8a/libpart1_gpubw.so` | Vulkan compute read, alone or beside a CPU stream (kit `gpubw`) | libc, libm, libdl, libvulkan |

Built by `./build.sh [OUTDIR]` (compiler logs go to `OUTDIR/logs/`; NDK printed, fails with exit 2 if none; API level 33; 16 KB LOAD alignment; `VERSION` = engine version; engine id `part1-engine/0.2.3`).
The plugin starts one process per row (`ProcessBuilder`, working directory = a writable directory of the plugin), reads **stdout** and takes the **last line** as the result (always a JSON object, see below). Exit codes: `EXIT-CODES.md`. Differences from the kit: `DIFF-FROM-KIT.md`.

**Confirmed by the planner (PLAN-023), recorded here:** (1) the defaults of the programs are the kit binary's (warm-up 2 s, window 3 s, 3 runs, 256 MiB per thread, 512 MiB for gpubw) and every row of the tables below passes its parameters explicitly, as the kit's `stages/core.sh` does (O02); (2) the build keeps `-march=armv8-a` (the kit-arm64 set used `armv8.2-a+fp16`; the kernel object code is identical, `raw/kernel-identity.txt`) (O04); (3) T3 is not an engine mode in this version: `S1-gpu-10min` and `S2-read-10min` are not run by the engine and `gpubw --loop-seconds` is refused with `--json` (O05).

## Result line

With `--json` a success prints exactly one `part1-rows-v1` object on the last stdout line (earlier stdout lines are the kit's human-readable output and `# pin ...` lines; stderr carries one-line messages). A refusal or error prints one object **with or without** `--json`. **The raw line validates against `descriptor-v02/part1-rows-v1.schema.json` as emitted** (tests check it with nothing removed and nothing added); the only record without a `tag` is a usage error reported before `--tag` was parsed, and the app adds the tag it started the process with. `--pin-probe` prints a different object (`part1-pinprobe-v1`, below), not a row; so do the two static probes of 0.2.2 (`libpart1_membw.so --static-probe`, `part1-staticprobe-v1`, and `libpart1_gpubw.so --probe`, `part1-gpuprobe-v1`, both below). Fields the program knows: `format, tag, kind, tier (if --tier), status, cpu_set, threads, buffer_mib, gbs_median, gbs_min, gbs_max, repeats, single_shot, passes, variant, pin{result,attempts,time_to_pin_ms}, exit_code, gate_basis, conditions{foreground_cpuset, gate_basis, buffer_mib, cpu_set, pin, memavail_mib, memtotal_mib, regime, threads, labels, note}, duration_s, duration_basis, engine_version, origin ("measured_app"), labels`.
Omitted (only the app knows): `thermal_status, thermal_headroom, battery_pct, charging, display_*, screen_on, start_temp_c, kit, comparable`.

Two top-level fields are **optional fields of the row schema** (descriptor-v02 `CHANGES-v0.2.md` P24): `reason` (string: refusal or error text, also appended to `conditions.note`; absent on a success) and `minflt_timed` (integer >= 0: minor page faults in the timed windows, summed over the runs; absent when nothing was timed). The app appends the line to the row log unchanged. A record written before the options were parsed (a usage error, or the exit 1 for a CPU list that cannot be read, which comes first) has no `tag`: the app, which started the process, adds it. A row without a value (any status other than `ok`) has `repeats 1`, `single_shot true` and null `gbs_*`, never a count left over from an earlier sweep size.

Value rules: `gbs_median` is the kit's "median of medians" (`mom`) over `repeats` runs of the kit (`--runs`); with one run `gbs_min`/`gbs_max` are `null` and `single_shot` is true. `passes` = timed passes of the last run. A sweep row's value is the largest size; every point is in `conditions.note` as `sweep total_MiB=GB/s: ...`. A GPU row's value is the kit's `mom` over `--dispatches` device-timestamp dispatches (repeats 1, `passes` = dispatches). `pin.attempts` and `time_to_pin_ms` are the worst over the threads. `pin.result` is `ok`, `unpinned` (a pin failed and `--allow-unpinned` was given in **any** timed run or sweep size of the process, or in the run in progress when a timeout record is written; the label `unpinned` is set), `failed` (exit 87: nothing ran unpinned, no `unpinned` label) or `not_applicable` (gpubw, or a record written before any pin result was known). Pin state is kept **per CPU for the whole process**: once a CPU has failed `pin_retry` under `--allow-unpinned`, later runs and later sweep sizes do not retry it (at most one 5 s wait per CPU per process) and run that CPU unpinned. Without `--allow-unpinned` nothing changes: exit 87 at the first failure. `gate_basis` is `cpuset_top_app`, `gate_off`, or `cpuset_not_top_app`.

**One rule for `cpu_set` and `pin` (0.2.2, made exact in 0.2.3 and 0.2.4; the same rule is in `EXIT-CODES.md`).** `cpu_set` and `conditions.cpu_set` (the same CPUs written `a+b`, or null when none) hold the CPUs the row asked for (the first `--threads` entries of `--cores`), with exactly one exception: an `ok` row whose `pin.result` is `unpinned` has `cpu_set []` and `conditions.cpu_set null`, because no CPU was pinned for all of it. Every record without a value (status `failed`, `skipped` or `unsupported`: exit 1, 2, 3, 87, 88, 97 and the 124 record) names the CPUs asked for, whatever its `pin.result`, once they are known (next paragraph). **When the CPUs are known.** For a **row or a sweep** they are known once `--cores` and `--threads` have been parsed and checked; for the **pacer** (`--pace-chase`, `--pace-idle`) at the start of `pace_main`, which comes after the foreground gate and the memory guard. A record written before that point has `cpu_set []` and `conditions.cpu_set null` whatever its status:
- every exit 2 raised while the options are parsed or checked (a bad value, an unknown option, `--cores` bad or listing a CPU twice, `--threads` too large, ...);
- the exit 1 written when the CPU list cannot be read (that check comes before `--cores` is parsed);
- **for the pacer, the exit 97 (foreground gate) and the exit 88 (memory guard):** both are raised before `pace_main`, so they have `cpu_set []`. (A row or sweep refused with 97 or 88 names its CPUs.)

A record written after that point names the CPUs asked for, including an exit 2 raised later: **a sweep size that is too small, whether it is the first size or a later one**, gives `cpu_set [..]` (a size after sizes that ran also carries `pin.result unpinned` when an earlier size ran unpinned, and `pin.result ok` when sizes ran pinned). The reason of that exit 2 is `sweep size <size> too small`, where `<size>` is the size as given **cut to its first 48 characters** (nothing marks the cut; the whole text is in the command line). In the 124 record `pin.result` is `unpinned` (with the label `unpinned`, `pin.attempts` and `time_to_pin_ms` the worst seen) when a pin has failed under `--allow-unpinned` in an earlier run, an earlier sweep size, or the run in progress; a `pin_retry` that is still waiting when the limit fires is not reported, and a timeout with no failed pin known says `not_applicable`. This holds for rows, sweeps and the pacer alike (0.2.1 had `cpu_set []` in some of these records and not in others). Tests: `TestH_A1_A2_A3`, `TestI2`, `TestI3`, `TestJ_CpuSetRule`.

**The note is never cut silently (0.2.2).** `conditions.note` holds at most 319 characters. When a sentence does not fit, the record gets the label `note_truncated` (also in `conditions.labels`). Sweep points have priority over the repeated and informational sentences (the gate-off sentence, the pin sentence), and so do the GPU dispatch rates (`dispatch GB/s: ...`): to make room the oldest of those are dropped first, and only if the priority text itself is still too long is it cut. A record whose note fits has no such label.

## Options

**0.2.4 behaviour worth knowing:** the OpenCL helper of `gpubw --probe` runs in its own process group and the whole group is killed at the end of each attempt; "loaded" is reported only when the helper wrote a `loaded` marker; the four attempts share an overall limit of 2.5 s (`not_tried`); the text output of the GPU probe prints `cpuset=` (see the GPU probe below). **0.2.3 behaviour worth knowing:** `gpubw --probe` records `foreground_cpuset` and loads each OpenCL candidate in a forked helper with a 2 s limit (see the GPU probe below); the pin probe reads the MIDR of a CPU whose pin failed without pinning (`sysfs_unpinned`, `cpuinfo_unpinned`); the exit 2 for a sweep size that is too small names the offending size in its `reason` (`sweep size 0.0001 too small`; 0.2.2 and earlier printed an unreadable text there). **0.2.2 behaviour worth knowing:** the engine has three more things than before: the rule for `cpu_set` and `pin` and the labelled note (above), the dispatch-rate list of a GPU row (B1, below), and the static probes (below). **0.2.1 behaviour worth knowing:** without `--json`, `libpart1_gpubw.so` behaves as the kit binary (a good `--loop-seconds` run, and a run in which every variant is skipped, exit 0 and print no `failed` line); the rule "never `ok` without a number" applies only with `--json`. `--tier` is checked before it is stored (a bad value gives a schema-valid exit-2 record without `tier`). `--cores` with the same CPU twice is a usage error (exit 2) for rows, as for the pin probe. The `kind` of a membw usage-error record is `sweep` when `--sweep` and `pacer` when `--pace-chase`/`--pace-idle` appears anywhere on the command line (else `read`).

Kit options keep their kit meaning and defaults (warm-up 2 s, timed window 3 s, 3 runs, buffer 256 MiB per thread, so the program with no row options behaves like the kit binary; **the T1/T2 rows below pass every parameter explicitly, as the kit's `stages/core.sh` does**). New or changed options are marked P1.

### Pin probe (`libpart1_membw.so --pin-probe`)

`libpart1_membw.so --pin-probe --cores LIST [--spin-ms 2000] [--json] [--gate on|off] [--max-seconds S]`. The gate applies (exit 97). For each CPU of `LIST` (explicit numbers such as `0,1,2` or `0+1`, or `all`; no duplicates), in the order given: the kit's `pin_retry` (unchanged: 50 ms retries for up to 5 s, mask and running CPU verified), then a short spin on that CPU that checks the running CPU. `--spin-ms` is the **total** spin budget (default 2000), divided over the CPUs (at least 1 ms each); a CPU whose pin fails costs at most the 5 s retry window and is reported `failed`: it does **not** fail the probe (exit 0). The affinity mask is restored after each CPU. Nothing is allocated, so there is no memory guard. `--max-seconds` applies (exit 124).

With `--json` the last stdout line is **one object that is not a row**, schema `part1-pinprobe-v1.schema.json` (this directory):

`{"format":"part1-pinprobe-v1","engine_version":"part1-engine/0.2.4","gate_basis":"cpuset_top_app","foreground_cpuset":"/top-app","status":"ok","exit_code":0,"cpus":[{"index":0,"result":"ok","attempts":1,"time_to_pin_ms":0.1,"midr":"0x412fd050","midr_source":"sysfs"}, ...],"duration_ms":2003.2}`

`status` is `ok` (the probe ran), `skipped` (gate, 97) or `failed` (usage 2, timeout 124, error); a refusal or error adds `reason` and `cpus` lists the CPUs completed so far. **Mapping onto the static input:** each `cpus[]` entry gives the `cpus[].pin` object of `descriptor-v02/part1-inputs-v1.md` (line 14: `pin {result ok|failed, attempts, time_to_pin_s, cpuset}`) for the CPU `index`: `result` and `attempts` are copied, `time_to_pin_s` = `time_to_pin_ms / 1000`, `cpuset` = `foreground_cpuset`; and `pin_conditions` takes `gate_basis` from the object. The row schema's `pinprobe` kind and tag stay unused in this version.

**MIDR per CPU (0.2.2).** Each CPU object also has `midr` (a hex string such as `0x412fd050`, or null) and `midr_source`. While the probe is pinned on that CPU (inside the spin) it reads `/sys/devices/system/cpu/cpu<n>/regs/identification/midr_el1` (`midr_source` `sysfs`); when that file is absent or cannot be read it takes the CPU's entry from `/proc/cpuinfo`, read in the same spin, and assembles the value from `CPU implementer`, `CPU variant`, `CPU part` and `CPU revision` (`midr_source` `cpuinfo`): `implementer << 24 | variant << 20 | 0xf << 16 | part << 4 | revision` (the `CPU architecture` line of cpuinfo says 8; the architecture field of the MIDR of an ARMv8 CPU is 0xf, which is what is used). When neither gives it, `midr` and `midr_source` are both null. **A CPU whose pin failed keeps its identity (0.2.3, planner decision PLAN-034).** For that CPU the same two sources are read without pinning (after the original affinity is restored): the sysfs file `/sys/devices/system/cpu/cpu<n>/regs/identification/midr_el1` does not need the reader to run on that CPU (`midr_source` `sysfs_unpinned`); if it is absent, that CPU's entry in `/proc/cpuinfo` if it has one (`midr_source` `cpuinfo_unpinned`); else `midr` and `midr_source` are null. `midr_source` is therefore one of `sysfs`, `cpuinfo`, `sysfs_unpinned`, `cpuinfo_unpinned` or null. The two fields are optional in `part1-pinprobe-v1.schema.json`: an object of 0.2.1 and earlier still validates.

Removed from the kit program (requirement 7): `--map uncached\|system` (`/dev/dma_heap`) and `--suite` (Pixel-6-Pro-only sequence). PMU counters (`perf_event_open`) in the pacer are still tried but optional; the JSON has no PMU field.

### libpart1_gpubw.so

Kit options (`--size-mb 512`, `--dispatches 5`, `--warmup-dispatches 20`, `--modes`, `--per-wg`, `--memtype`, `--src-memtype`, `--dst-memtype`, `--stage`, `--hot-ms`, `--loop-seconds`, `--timeline`, `--csv`, `--tag`) plus the P1 options `--json`, `--gate`, `--mem-limit-mib`, `--fit-buffer`, `--max-seconds`, `--tier`, `--row-kind gpu|pacer`, and the labels `--cpu-set LIST --cpu-threads N` (the CPUs and thread count of the CPU stream running beside it, copied into `cpu_set` and `threads`; no effect on the measurement). `--probe [--json] [--max-seconds S]` is the GPU probe (see "Static probes"; no other option is allowed with it). `--allow-unpinned` is accepted and ignored (gpubw never pins; `pin.result` is `not_applicable`). With `--json` exactly one mode and one `--per-wg` are required, both must be what the kit's loop would measure (a mode is one integer 0..5; a per-wg is a positive integer that divides the buffer in 16-byte units, is a multiple of 1024 (2048 for mode 4, 4096 for mode 5) and gives 1..65536 workgroups, for example 4096) or the program exits 2 with `status failed` and a reason; it never reports `ok` without a number. `--loop-seconds` is refused (T3 sustained is not part of this engine version). The memory guard counts 2 buffers of `--size-mb` (3 with `--stage`). `--memtype` without `--stage` is a research option outside the guard's count: with a device-local type it allocates 3 buffers although only 2 are counted; the rows of this document never use it. With a CPU stream beside the GPU row (C8) the GPU row gets the same `--mem-limit-mib L` as the stream, **computed after the stream has started** (no subtraction: `MemAvailable` then already reflects the stream's buffer).

**GPU dispatch rates (0.2.2, planner decision after the P1-03S review F205).** With `--json`, `conditions.note` of a GPU row carries every timed dispatch's rate in dispatch order, `dispatch GB/s: a, b, c, ...` (two decimals, 1 GB = 1e9 B, `bytes / device-timestamp ns` of each timed dispatch). When the largest of them is at least 1.25 times the smallest (equivalently the slowest dispatch took at least 1.25 times as long as the fastest) the record gets the label `gpu_rate_unstable` (in `labels` and `conditions.labels`); exactly 1.25 is unstable, 1.24 is not. The row value stays the kit's `mom` (the median of the dispatches); nothing about what is measured has changed. On D1 the GPU-alone value depends on a memory-clock governor that idles down (P1-03S F205); the list and the label let the app and Part 2 see it in the row.

### Static probes (0.2.2)

Both probes measure nothing, need no pinning and no large memory, finish in well under 1 s, and print with `--json` **one object that is not a row** (not a `part1-rows-v1` record: no tag, tier, bandwidth or pin). The foreground gate does not apply to them (they run at every plugin start); they record the cpuset they saw. Usage errors and failures follow the existing rules: one JSON object of the same format with `status failed`, `exit_code` and `reason` (and no data fields), exit 2 for a usage error, 124 for `--max-seconds`; the exit codes are in `EXIT-CODES.md`. Without `--json` a success prints `# static-probe ...` / `# gpu-probe ...` text lines and no object.

#### `libpart1_membw.so --static-probe [--json] [--max-seconds S]` -> `part1-staticprobe-v1`

Schema: `part1-staticprobe-v1.schema.json` (this directory). Fields: `format`, `engine_version`, `status` (`ok`), `exit_code`, `page_size` (`sysconf(_SC_PAGESIZE)`), `hwcap` and `hwcap2` (`getauxval(AT_HWCAP)` / `AT_HWCAP2`, hex strings), `features` (booleans decoded from them: `asimd` HWCAP bit 1, `asimdhp` (fp16) bit 10, `asimddp` (dotprod) bit 20, `sve` bit 22; HWCAP2: `sve2` bit 1, `i8mm` bit 13, `bf16` bit 14, `sme` bit 23), `cpus_possible`, `cpus_present`, `cpus_online` (the text of `/sys/devices/system/cpu/possible|present|online` as read, trailing newline removed, or null when unreadable), `properties` and `foreground_cpuset` (own `/proc/self/cpuset` as read, or null; no gate). `properties` holds the values from `__system_property_get` for **exactly this fixed list and no other**, in this order: `ro.board.platform`, `ro.hardware`, `ro.product.board`, `ro.product.device`, `ro.soc.model`, `ro.soc.manufacturer`, `ro.build.version.sdk` (the empty string when unset). The list is compiled in and cannot be extended from the command line (any other option is a usage error); there is no serial, no fingerprint and no network property in it, and the program reads no other property (tests check the source and the arm64 binary for property names). Example: `{"format":"part1-staticprobe-v1","engine_version":"part1-engine/0.2.4","status":"ok","exit_code":0,"page_size":4096,"hwcap":"0x...","hwcap2":"0x...","features":{"asimd":true,...},"cpus_possible":"0-7","cpus_present":"0-7","cpus_online":"0-7","properties":{"ro.board.platform":"...",...},"foreground_cpuset":"/top-app"}`.

#### `libpart1_gpubw.so --probe [--json] [--max-seconds S]` -> `part1-gpuprobe-v1`

Schema: `part1-gpuprobe-v1.schema.json`. Fields: `format`, `engine_version`, `status`, `exit_code`, `vulkan` and `opencl_child`. `vulkan.available` is a boolean; when true there are `device_name`, `device_type`, `vendor_id`, `device_id`, `api_version` (`major.minor.patch`), `driver_version` (the number the driver reports), `compute_queue` (a queue family with the compute bit exists), `shader_float16`, `shader_int8`, `integer_dot_product` (booleans; **null when the query is not available**: the feature structs are chained for the extension when the device lists it, else for the core struct when the lower of the instance and device version has it, else the answer is null) and `memory_heaps_mib` (the size of each memory heap in MiB). Only the instance and the physical-device queries are made: no device, no buffer, no memory is created. **No Vulkan device is not an error:** exit 0, `vulkan.available false` (with a `reason`). The device queried is the first one, the one the measurement uses.

`opencl_child` is a list of four entries, one for each candidate name in this order: `libOpenCL.so`, `libOpenCL-pixel.so`, `/vendor/lib64/libOpenCL.so`, `/system/vendor/lib64/libOpenCL.so`; each has `name`, `loaded` (whether `dlopen` succeeded), `outcome`, `error` and `signal`. **Since 0.2.3 each `dlopen` attempt runs in a forked helper process** (a vendor library's start-up code runs inside `dlopen` and cannot kill the probe). `outcome` is `loaded`; `dlerror` (`error` holds the `dlerror` text); `crashed` (`signal` holds the signal number that ended the helper); `timeout` (the helper was still running at its limit, or was ended by its own alarm, and was killed and collected); `not_run` (the helper could not be started; `error` says why); or, since 0.2.4, `not_tried` (the overall limit was used up before this candidate was started). `error` is a string only for `dlerror` and `not_run`, `signal` an integer only for `crashed`.

**How the helper is run (0.2.4).** The helper is silent (its stdin, stdout and stderr are `/dev/null`), dies with the probe (`PR_SET_PDEATHSIG`), carries its own 3 s alarm and **runs in its own process group**. When the attempt ends, whether the helper finished, crashed or ran out of time, the parent kills the **whole group** with SIGKILL and collects the helper; the `--max-seconds` watchdog kills the group too. A process that the library's start-up code starts therefore does not survive the probe, **unless it leaves the group itself** (`setsid` or `setpgid`): nothing here can stop that, and a probe killed with SIGKILL cannot kill the group (the helper still dies with it; a grandchild would not). The helper writes `L` on a pipe when `dlopen` returned, or `E` and the `dlerror` text when it failed, and the parent reads the pipe **after** the helper was collected, so the text cannot be lost. **`loaded` is true only when the `L` marker was read and the helper exited with status 0:** a library whose start-up code calls `exit(0)` never returns from `dlopen`, so it is `dlerror` with the text `helper exited with status 0 before dlopen returned (no loaded marker)`. A helper ended by its own alarm (for example when the probe was stopped for more than 3 s) is `timeout`, not `crashed`. The helpers run before any Vulkan call.

**Duration.** Each candidate has a limit of 2 s, and the four together share an **overall limit of 2.5 s** (a candidate gets the smaller of 2 s and what is left). **Worst case, four hanging candidates:** the first runs 2.0 s and is `timeout`, the second gets the remaining 0.5 s and is `timeout`, the third and fourth are `not_tried`; the OpenCL part ends after 2.5 s and the whole probe within 3 s (0.2.3: 8 s). Under `--max-seconds` below 3 the 124 object comes first, as before. In the normal case the probe takes well under 1 s; the probe itself always ends with its JSON object. The object also has `foreground_cpuset` (0.2.3: own `/proc/self/cpuset` as read, or null; no gate), as the static probe has; the text output (without `--json`) prints it as `cpuset=` on its first line (`-` when unreadable). **`opencl_child` is the result for a child process, which may differ from loading inside the app process** (the app's linker namespace and the child's are not the same): it says what a native child of the plugin can use, not what the app can.

**What the phones showed (P1-03P, engine 0.2.3).** On D1 and D5, in a child started by the app, every OpenCL candidate failed to load (library not found, or "not accessible for the namespace (default)"), while from the adb shell all four loaded on D1. **`opencl_child` therefore says nothing about loading inside the app process, and must not be used as "OpenCL available".** A consumer that wants the OpenCL backend has to load the library itself, in its own process.

## T1 rows (plan 3.2). `L` = the app's limit `min(55 % MemTotal, 70 % MemAvailable)`; `<k>` = cluster id; `<cpu>` etc. from the pin probe (`--pin-probe`)

Common tail for every row: `--json --tier T1 --mem-limit-mib L --fit-buffer --max-seconds 120` (kit timeout of these rows: 120 s). **Every T1 and T2 command line carries `--fit-buffer`** (a row written as `... + tail` gets it from the tail, which is stated once and not repeated in the row), because the kit always shrank the buffer and labelled the row (`lib/ilib.sh` `@MEMSIZE`). A `smaller buffer` row is labelled and is not comparable with a full-size row (nor with the kit's reference): the app keeps the label and does not mix it with unlabelled rows. ## Starting from the plugin

Run with the plugin's native directory as the executable path (`app_plugin_native_libs/<pluginId>/libpart1_membw.so`, mode 0755 set by the host extractor) and a writable working directory. Environment: nothing needed. The program reads only `/proc/self/cpuset`, `/proc/meminfo`, `/proc/cpuinfo` (`processor` and `CPU part` lines; if it has no `CPU part` lines the affinity mask is used) and, with `--cpufreq-log`, `scaling_cur_freq`.
