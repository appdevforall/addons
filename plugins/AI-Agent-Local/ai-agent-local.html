AI Agent Local Plugin

Executive overview

AI Agent Local runs large-language models entirely on the device. It registers itself as the local inference backend with AI Core, which routes requests from the Agent chat, Code Suggestions, Speech to Text and Vector Search. It also contributes its own settings pane — the model picker and the checks around it — which AI Core mounts inside Agent settings.

Install AI Core alongside it — without the router this plugin has nothing to register with. Install order does not matter.

This plugin declares no INTERNET permission. Prompts, code and generated text cannot leave the device, because the plugin has no way to send them anywhere.

Core functionality

  • On-device GGUF inference through a bundled, prebuilt llama.cpp library.
  • Streaming responses, with Stop cancelling the native generation early rather than waiting for it to finish.
  • Chat with history, rendered in the ChatML format that on-device instruct models are fine-tuned on.
  • Model safety checks — inspects a selected .gguf header and refuses embedding-only models for chat, with a clear error instead of a native crash.
  • Actionable load failures — a failed load is classified (no longer reachable, streamed rather than local, empty, not a GGUF, out of memory, unsupported quantization) and reported as a message that says what to do next.
  • Direct storage access — a model chosen as a content:// document is read in place, through the read grant the picker persisted. Nothing is copied into private storage, so a multi-gigabyte model costs no device space beyond the file you downloaded.
  • Its own settings pane — browse for a .gguf file, re-load the model already selected, record the model's published SHA-256, and choose between the short system prompt small models follow reliably and the full tool-calling one. A model too large for the device's free RAM raises a warning first.

Technical architecture

ComponentRole
LocalLlmPluginPlugin entry point. Registers the backend with AI Core on activation, re-registering if AI Core activates later; frees the native model on dispose.
LocalLlmBackendThe inference engine. Opens the selected model in place and hands the native loader that descriptor, manages loading and unloading, and serializes generations against the shared native context.
GgufModelInspectorMinimal GGUF header reader that classifies a model as chat- or embedding-only.
ModelLoadDiagnosticsClassifies a load failure from the model's size and readability, free memory and the native error text, as a pure function that is unit-tested off-device.
ModelLoadMessagesRenders a diagnosis as user-facing text, keeping string resources out of the engine.
LocalLlmSettingsFragmentThe settings pane AI Core mounts: model browser, load-from-saved, SHA-256 verification and the prompt-format toggle, plus the low-memory warning dialog.

The native library is committed prebuilt, so a normal build needs no NDK, CMake, or the llama.cpp submodule. Packaging is limited to arm64-v8a: the IDE extracts a single ABI and ships no x86 build, so this plugin requires a 64-bit ARM device.

Usage

  1. Install AI Core and AI Agent Local via the Plugin Manager, then restart the IDE.
  2. Open Preferences → Configuration → Agent and select the local backend. This plugin's own pane appears below it.
  3. Tap Browse and pick a .gguf model file. It is loaded from wherever you saved it, with no copy made; a model larger than the free RAM asks you to confirm first. Leave the file in place — moving or deleting it breaks the selection. The picker offers device-local documents only: a model still in a cloud folder can only be read as a stream, which the in-place loader cannot use.
  4. Optionally record the model's published SHA-256, or use Load from saved to return to the model you already selected.
Model choice drives whether this works at all on a given device. A Q4_K_M quantization of a 1–3B parameter model is the safest starting point; larger models need more free RAM for the KV cache than the file size alone suggests.

Key benefits

  • Complete privacy — no network permission, so code and prompts cannot be transmitted.
  • Works offline — no connectivity, account, or API key needed.
  • No running costs — no per-token billing or rate limits.
  • Crash-resistant — model classification and header bounds-checking turn would-be native crashes into recoverable, user-visible errors.
  • Reproducible builds — no NDK required; the native library ships prebuilt.
