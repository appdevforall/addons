1. Executive Overview

Flutter Templates is a template bundle for Code on the Go. It adds ready-to-use Flutter starter projects to the New Project screen, sitting alongside the built-in core (Android) templates. Instead of starting from an empty folder, a developer picks a Flutter template, enters an app name and package name, and the IDE generates a complete, idiomatic Flutter project skeleton.

The bundle contributes five templates — one for a plain Flutter app and four wired to popular state-management libraries — so a project starts with the chosen architecture already in place.

It runs no code. A .cgt bundle is a zip archive of project skeletons and their metadata, which the IDE reads directly. There is nothing to enable, no permissions to grant, and no process to load.

What each template generates

Every template produces a small counter app so the chosen pattern is demonstrated end to end:

  • pubspec.yaml — project name (lower-cased from the app name), the SDK constraint, and the state-management dependency.
  • lib/main.dart — the app entry point and home screen.
  • A pattern-specific source file where applicable — e.g. lib/blocs/counter_bloc.dart, lib/providers/counter_provider.dart, or lib/controllers/counter_controller.dart.
  • analysis_options.yaml — a lint baseline.
  • README.md — getting-started notes for the generated project.

Parameter substitution

The app name and package name entered in the New Project dialog are substituted into the generated files. The app name also drives pubspec.yaml's name: field, lower-cased to satisfy Dart's package-name rules.

3. Technical Architecture

What is in the archive

A .cgt is a zip archive. Its root holds templates.json, which lists the templates, and one directory per template. Each of those carries template/template.json for its name, description and parameters, and template/thumb.png for the picture on the New Project screen.

flutter-templates.cgt | +-- templates.json lists the five templates +-- cgt-build.properties the commit this bundle was built from | +-- FlutterBasic/ | +-- template/template.json | +-- template/thumb.png | +-- pubspec.yaml.peb | +-- analysis_options.yaml | +-- lib/main.dart.peb | +-- FlutterBloc/ ... and three more

Authoring with Pebble

Files ending in .peb are processed by the Pebble template engine at project-creation time (${{APP_NAME}}, ${{PACKAGE_NAME}} and friends are substituted) and the suffix is dropped; other files are copied verbatim. This is the same authoring format the core Android templates use. Dart's own $variable string interpolation passes through untouched, because it does not match Pebble's ${{ }} delimiter.

How the IDE finds it

Code on the Go discovers project templates by scanning its templates directory and the Downloads folder for .cgt archives. Putting the file in either place is the whole installation. Nothing registers it, because there is no code to run.

Provenance

Every published bundle carries cgt-build.properties at its archive root, recording the commit it was built from and the date of that commit. Read it with unzip -p flutter-templates.cgt cgt-build.properties. It exists so a bug report can be traced to the exact source that produced the file, which matters because the download URL stays the same across releases.

Permissions

None. A template bundle declares no permissions, because it runs no code. No network, no native code, no system commands, no filesystem access of its own — the IDE writes the generated project, exactly as it does for a built-in template.

4. Usage

Install

  1. Download flutter-templates.cgt from the add-on gallery.
  2. Open the Templates manager in Code on the Go. It scans the Downloads folder, so the bundle appears with its five templates listed.
  3. That is all. There is nothing to enable.
Replacing the old plugin. Earlier releases shipped these templates as a plugin. If you still have Flutter Templates installed in the Plugin Manager, disable or uninstall it before adding this bundle. Otherwise each template appears twice, once from each source. Disabling the plugin removes its copies.

Create a project

  1. Open New Project.
  2. Pick one of the Flutter templates (Basic, BLoC, Provider, GetX, Riverpod).
  3. Enter an app name (a valid Dart package identifier — lowercase, no spaces; underscores are fine) and a package name.
  4. Finish the wizard. The generated project appears in your workspace.
Building the generated project requires the Flutter SDK, which Code on the Go does not yet provide on-device. Run flutter pub get / flutter run on a machine with Flutter installed, or once an on-device Flutter SDK becomes available.

5. Key Benefits

  • First-class integration. Templates appear on the standard New Project screen next to the core templates — no separate UI to learn.
  • Architecture on day one. Pick your state-management approach up front and start from working, idiomatic boilerplate.
  • Parameterized. App name and package name flow into the generated files, including a Dart-valid pubspec.yaml name.
  • No code, no permissions. A data bundle the IDE reads. Nothing loads into the editor's process, so there is nothing to grant and nothing to go wrong at runtime.
  • Plain text throughout. Every template file is readable and reviewable. The download is the source.
  • Traceable. Each published bundle records the commit it was built from, so a report about one download points at one commit.

6. Limitations & Scope

  • The bundle scaffolds project files only; it does not install the Flutter/Dart SDK or build/run Flutter projects on-device.
  • Code on the Go's editor does not currently provide Dart syntax highlighting, completion, or analysis — these templates create the files, but rich Dart editing is outside the IDE's current language support.
  • On-device Flutter toolchain support is a separate, larger effort tracked independently.
